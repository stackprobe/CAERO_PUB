# ワープ停止時間の調査（2026-10-22）

## 結論

現在のワープは、Eの入力を処理する描画スレッドで、移動先を含む **25島を同期的に生成・登録・GPU転送** する。9島ではない。座標を書き換えた後もこの処理から戻らないので、準備が完了するまで次の画面が描画されない。

実測の大半はCPUによる島生成だった。特に既存の方位盤・島番号・行き先表示の面加工と、新しいワープ階・装置の面加工が重い。ワープ実装で通常の明示的テレポート用の同期ロードをそのまま呼び出したことと、1島の生成コストを十分に考慮しなかったことが今回の停止につながっている。

この調査ではゲーム本体の動作は変更していない。計測用の変更は `tmp/warp-profile/` の複製プロジェクト内に限定した。

## 実行経路

- `Program.cs` のE入力処理から `WarpTravel.Travel` をそのまま呼ぶ。
- `Sector.Warp.cs` の `Travel` は `World.Teleport` の `radius` を指定しない。
- `World.cs` の `LoadRadius` は **2**。正方形の半径なので `(2×2+1)² = 25島` になる。
- `Teleport` は移動元の島を解放し、`EnsureAround` を同期実行する。そこで各島の `Sector.Generate` と `Install` を直列に呼ぶ。
- `Install` はCPU生成後にGPUモデルを転送する。実際の出現位置は、その後の `destinationView` で確定する。
- 通常の移動では `World.Update` が `Task.Run` で1島ずつ生成するが、このワープの同期処理はそれを利用していない。

島のファイル25個を読む処理ではない。地形・建築・面加工・当たり判定・人物配置を、その場で計算している。

## 同期ロード数の比較

現在のコミット `746bc64` のソースを複製し、Release構成、ワールドシード1701、`(-43,-33)` の北46装置から `(-43,-79)` へのワープを計測した。移動元は25島を保持し、移動先との再利用はない。完全なワープ処理でウォームアップ後、各条件3回の中央値。比較のため、複製側だけに半径の引数を追加した。

OpenGLコンテキストを用意し、モデルのGPU転送・移動元モデルの解放を含めた。音声とシーンの描画は実行していない。測定前の `glFinish` で以前のGPU処理を完了させ、測定後のGPU完了待ちは別に記録した。したがって、実ゲームの前フレームの描画待ちなどを含むE入力から表示までの完全な測定ではない。

| 同期生成する範囲 | 新規生成島数 | GPUモデル数 | ワープ呼び出し時間の中央値 | 累積マネージド確保量 |
| --- | ---: | ---: | ---: | ---: |
| 現状：半径2、5×5 | 25 | 50 | 3,127 ms | 6,477 MiB |
| 比較：半径1、3×3 | 9 | 18 | 1,129 ms | 2,342 MiB |
| 比較：到着先1島のみ | 1 | 2 | 134 ms | 263 MiB |

25島条件の3回は3,130 / 3,127 / 3,073 ms。9島でも約1.1秒なので、半径を1へ変更するだけでは入力時の停止は残る。1島でも約0.13秒のため、停止をなくすには到着先の生成も非同期化する必要がある。

## 時間の内訳

25島条件の中央値に相当する試行（3,127 ms）：

| 処理 | 時間 |
| --- | ---: |
| CPUで25島を生成 | 3,032 ms |
| 生成後の登録・GPU転送・CPU描画用配列解放など | 88 ms |
| 移動元25島の解放 | 7 ms |
| 到着位置の確定・魚のリセット | 0.1 ms未満 |

CPU生成3,032 msには、既存の案内表示の生成1,235 ms、ワープ階・装置の生成849 ms、高層・浮遊建築生成419 msなどを含む。ワープ849 msの内訳は床番号の埋め込み257 msと、200台の装置生成591 msがほぼ全て。高層・浮遊建築419 msのうち、新設外階段を含む浮遊建物の重複面除去は313 msだった。

登録88 msのうち、頂点等をネイティブ配列に詰める処理が36 ms、`Raylib.UploadMesh` 呼び出しが14 ms。測定後のGPU完了待ちは約1 msだった。今回の測定では、GPU転送待ちが秒単位の停止の主因ではない。

## メモリ確保と面加工

割り当て内訳を追加した別の3回計測でも、中央値は3,158 msだった。その試行の累積確保量は以下のとおり。内訳中の子項目は親項目に含まれるので重ねて加算しない。

| 処理 | 累積マネージド確保量 |
| --- | ---: |
| ワープ全体 | 6,477 MiB（約6.3 GiB） |
| CPU島生成全体 | 6,458 MiB |
| 既存の方位盤・番号・行き先表示 | 2,685 MiB |
| ワープ階・装置 | 2,534 MiB |
| └ ワープ階の床番号埋め込み | 685 MiB |
| └ 8台×25島の装置生成 | 1,846 MiB |
| 高層・浮遊建築 | 662 MiB |
| └ 浮遊建物・外階段の重複面除去 | 443 MiB |

これは常駐メモリ量ではなく、1回のワープ中に作られるオブジェクトの累積確保量である。1島あたり約259 MiB。世代別のGC回数カウントもGen0=480 / Gen1=147 / Gen2=48と増えた。各世代のカウントは合算しない。GC停止時間自体は今回分離計測していないため、停止の全てをGCへ帰属するものではない。

コード上の重い箇所：

- `Sector.Wayfinding.cs` の `ApplyWayfindingInlay` は、床・壁の小さな表示を入れる際に `Stone.Inlay` を呼ぶ。
- `Sector.Warp.cs` の床番号も同じ処理を使い、床板1枚に対して島全体の建築メッシュを加工する。
- `Geometry.Inlay` → `RemoveCoplanarPass` は建築三角形を走査し、対象表示と交わらない面でも面情報・分割用リストなどを作り、頂点・法線・色の配列を再構築する。1島の中でも複数回実行される。
- 装置は1台ごとに数字の面加工と一般的な重複面除去を行う。島1つでは8台だが、同期25島では200台をE入力中に組み立てる。

同種の全メッシュ走査と一時割り当ての問題は、以前の `WAYFINDING_PERFORMANCE.md` の生成負荷調査でも確認されている。今回はワープ階・装置・外階段の生成も加わり、これを25島分まとめて待つ経路になった。

## 改善の優先順

1. **E入力の処理から同期25島生成を外す。** 到着先1島をバックグラウンド生成し、用意できたらGPUへ登録して安全な位置へ移動する。準備中に入力・画面更新を止めず、床が存在しない場所で物理だけ進めないよう遷移状態を設ける。
2. **周囲は既存の非同期ストリーミングで補う。** まず到着先を優先し、近隣を距離順に生成・登録する。9島を即座に揃えることを移動の完了条件にすると、依然として約1秒待つ。
3. **番号表示の加工範囲と回数を減らす。** 島全体ではなく対象の床板・壁面だけを加工し、可能な表示はまとめて処理する。装置の図柄も、生成済みの面を再度一般的な重複除去へ通す方式を見直す。

これらは調査からの改善方針であり、この測定時点ではゲーム本体へ適用していない。
