# 方位盤・番号プレートの性能調査（2026-10-19）

## 確認したこと

静止して番号プレートを見る際の負荷は、比較測定ではプレートの有無よりも、その視点でのシーン描画に支配されていた。番号プレート・方位盤を両方外しても、保存視点の描画時間はほぼ変わらなかった。解像度を縦横半分にすると大きく短縮したため、主な調査・改善対象はGPUの画素処理と帯域である。

これとは別に、埋め込みのため島全体の建築メッシュを再加工する処理に、生成時間とメモリ確保量の増加を確認した。こちらは島生成時の問題であり、静止時のGPU使用率を直接説明するものではない。

この調査ではゲーム本体の性能修正は行っていない。

## 静止視点の比較

- シード1701、島座標 `(140, -2)`、位置 `(37.0811, 1.75, -12.930007)`、Yaw `-227.0459`、Pitch `0.07980251`。保存視点を使い、添付画像と同じ番号77983の壁面を確認した。
- Intel UHD Graphics、通常ウィンドウ1440×900、昼の時刻150秒、描画用時刻12秒。音声と移動・ストリーミングを除外し、25島を固定して比較した。報告画像の読み込み数30とは異なる。
- FPS制限を解除し、各視点48フレームのうち最初の12フレームを除いた中央値。描画の前後に `glFinish` を入れ、GPU完了まで待つ時間を測った。GPUタイムスタンプ単独ではなく、CPUの描画命令発行も含む経過時間である。
- 本体のソースを複製した一時計測プロジェクトで、埋め込み生成だけを切り替えた。追加前のワールドシェーダーとの比較も実施した。

| 保存視点の条件 | 描画時間の中央値 |
| --- | ---: |
| 番号プレート・方位盤なし | 17.4411 ms |
| 番号プレート・方位盤あり | 17.4529 ms |
| 両方あり、720×450 | 5.8875 ms |

同じ位置からプレートへ正対した近接視点でも、両方なし20.3498 ms、両方あり20.4992 msだった。別の4条件比較では番号プレートだけを追加した場合も大きな増加はなかった。

したがって、この環境と視点では「プレートだけが静止中の大幅な速度低下を起こす」という差は確認していない。GPU使用率の上限到達だけでは、その負荷をプレート単体に帰属できない。

## 描画処理の内訳

保存視点を空・ワールド・後処理に分け、各境界でGPU完了を待った別測定。同期が増えるため、上記の一括測定とは総時間が異なる。

| 処理 | 両方なし | 両方あり |
| --- | ---: | ---: |
| 空 | 2.3235 ms | 2.2394 ms |
| 建物・地面・人物・海など | 11.3278 ms | 11.5788 ms |
| 画面全体の後処理 | 4.3882 ms | 4.2508 ms |

最大の負荷はワールド描画だった。調査用に素材模様の処理を省くとワールド部分は8.6003 ms、照明ループを省く別実験では8.4237 msになった。見た目を変更する切り分け実験であり、製品の修正としては適用していない。これらの改善幅は相互に独立とは限らず、加算できない。

`Shaders/world.fs` の素材模様・照明処理と、`Shaders/post.fs` の全画面フィルターが改善候補。プレートも共通のワールドシェーダーを通るが、文字のポリゴンを減らすだけでフレーム全体の負荷が解消するとは、この比較結果からはいえない。厳密なGPU内の律速箇所は、専用プロファイラーでの追加確認が必要。

## 別途確認した島生成の負荷

Release構成、段階的JITコンパイルを無効化し、島 `(140, -2)` を繰り返し生成した比較。メモリ量は生成1回あたりの累積マネージドメモリ確保量であり、常駐量ではない。

| 条件 | 生成時間の中央値 | 確保量 |
| --- | ---: | ---: |
| 両方なし | 31.2241 ms | 約24.16 MB |
| 番号プレートのみ | 35.8579 ms | 約47.61 MB |
| 方位盤のみ | 31.6688 ms | 約51.96 MB |
| 両方あり | 50.6187 ms | 約76.71 MB |

時間にはGC等によるばらつきがあるが、メモリ確保量の増加は明確だった。原点と `(-40, -87)` でも確保量の増加を確認した。

原因は `Sector.Wayfinding.cs` が方位盤と番号プレートでそれぞれ `Stone.Inlay` を呼び、`Geometry.RemoveCoplanarPass` が毎回全ての建築三角形を走査すること。対象面以外でも分割用リストや候補列挙を用意し、頂点・法線・色の配列を作り直している。対象島の番号プレートだけの面加工は、別の20回測定で中央値14.5914 ms、平均約20.11 MBを確保した。

240フレームの移動・ストリーミング実験でも、累積確保量は両方なし約484 MBから両方あり約1294 MB、GC停止時間の合計は約157 msから約258 msへ増加した。ただし、この実験の中央値や最大フレーム時間に大幅な悪化はなく、実行中の追加島数にも1島の差がある。静止時の症状の根拠とは分けて扱う。

生成側の改善方針は、島全体を二度加工する代わりに埋め込み対象の壁・床だけを処理し、同一平面の装飾の細かい図柄を当たり判定へ持ち込まないこと。

## 計測資料

一時計測プロジェクトと生ログはワークスペースの `tmp/plate-profile/` に保存した（Git管理対象外）。`saved-*.log` が静止視点、`gpu-stages-*.log` が描画内訳、`cpu-*.log` と `stages-*.log` が生成・衝突判定、`stream-*.log` が移動中の測定。計測用のソース・シェーダー変更はこの一時プロジェクト内に限定した。
